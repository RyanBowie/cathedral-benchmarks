The scoreboard

Two lenses. The benchmark score is 0–10 across seven weighted criteria, scored harshly in the same spirit as the cat benchmarks: a 10 would be indistinguishable from a survey-grade model of the real building. Alongside it are the pack's own rubric scores out of 100 (functional pass ≥ 85, visual pass ≥ 80), which are reported separately and never averaged.

0–2 missing or broken3–4 crude5–6 recognisably Cologne7–8 convincing and detailed9–10 near survey-grade (not reached yet)

The matrix

Provisional scores. One reviewer, one run per model. Each criterion maps to the requirement IDs in the pack's RUBRIC.md, and every build has a full result record (example) with item-by-item rubric scores. Edit SCORES in index.html and everything recalculates.

The builds

A managed app can't be embedded outside its player, so every build is also published here as a static mirror: the app's own production bundle, unchanged, served by GitHub Pages. Launch the live build to use the real thing in a new tab; the clip is recorded from that mirror.

Credits and time

Context, not the verdict. Credits are the single cumulative cost of the completed app (RUBRIC §1.6). Time runs from the kickoff prompt to the final build verified live in the managed-app player.

What every model gets

The pack is research material, not a specification: no prescribed dimensions, coordinates or colours. Each model researches the building and builds its own interpretation, and is judged on whether it is recognisably Cologne and works well. Reviewer-only data (measured proportions, colour targets, Blender proofs) is kept out of the pack.

What the app must do

  • Run in Copilot Managed Runtime, with a 2D fallback if WebGL fails.
  • Orbit, pan, zoom, at least 8 named views, Home, focus on a point.
  • At least 6 levels from the excavations to the spire tips; exterior, interior and x-ray; horizontal and long-section cuts; a live minimap.
  • At least 20 sourced hotspots, search, a guided tour, key figures as 3D labels, sun and night lighting, and the south-tower climb.
  • 30 fps or better, usable at 1024 × 768, accessible, with credits and an "approximate model" statement.

Two tracks

Track A: all geometry generated procedurally in the app. Track B: the model writes a headless Blender script that the operator runs, and the app loads the result. Separate leaderboards, never pooled. Every build so far is Track A.

How they were built and judged

GitHub Copilot app → managed runtime

The model runs in its own GitHub Copilot app session (autopilot, maximum reasoning) with the pack attached, scaffolds a managed app with the ms CLI, and deploys it to Copilot Managed Runtime itself.

Pack + prompt→Research→Build & self-test→Deploy→Verify in player

Static mirror

After the run, the operator copies the app's production build (dist/) into builds/<model>/, byte for byte, with no prompt to the model, so its credits stay clean. A headless check confirms it loads with no errors and no external requests before publishing.

Apps that call managed-app data sources would need stubs to run statically; none so far.

Ground rules

  • Same pack version and fixed kickoff prompt every time.
  • Highest reasoning setting; exact model label recorded.
  • A new session, run folder and managed app per run, with memory frozen.
  • No hand edits: each mirror is the model's own build output.
  • Repairs only as evidenced repair prompts, counted and disclosed.

Why a cathedral?

Research, not recall

Unlike a cat, nobody can build Cologne from memory. The model has to read plans, sections and photos, take its own measurements and turn them into believable proportions.

A real managed app

Scaffolding, building, deploying and verifying inside Copilot Managed Runtime, under its content-security policy, is part of the test, as it would be for any business app.

Long-horizon engineering

Hundreds of thousands of triangles, instancing, sections and a full UI, built and tested over hours. It exposes planning, self-testing and how a model copes with context limits.

Caveats. One run per model and one reviewer, so luck and taste matter. Rubric items rest on the model's in-player evidence plus an independent reviewer check of the static mirror. The first run (Claude Opus 5.5) predates the isolation protocol: its working folder was the whole benchmark tree, including reviewer-only notes, and it could read earlier session history. Later runs use an isolated run folder.
